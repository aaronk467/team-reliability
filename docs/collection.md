# Collecting defensible response data

The intended user is a dispatch supervisor reviewing response variation by service zone and priority. Start with existing computer-aided dispatch event logs. Where no system exists, provide staff a short form with an event identifier, zone, priority, dispatch time, arrival time, and optional delay reason. Capture timestamps automatically when possible; manual entry needs date, timezone, and a documented correction process. Synchronize dispatch and vehicle clocks to the same trusted time source and audit drift. Do not enter patient information.

Define dispatch and on-scene events consistently before collection. This tool measures dispatch-to-arrival time, not call-answer-to-arrival, treatment quality, survival, or ambulance availability. Include consecutive eligible dispatches across all shifts and zones, not a convenient sample. Record priority at dispatch and preserve changes separately. Document zone definitions and any boundary or triage policy changes.

Keep a separate complete intake register of all dispatches, including unresolved, canceled, duplicate, mutual-aid, and missing-arrival records, with explicit status and exclusion reasons. The statistical API supports completed calls only. The dashboard also provides a separate browser-local open-call register; this is a demonstration workflow, not an agency-wide intake database. Do not fabricate arrival times or silently classify unfinished calls as successful. Resolve records when an arrival becomes available; report counts and characteristics of excluded and still-open calls alongside the completed-call analysis. Long-running unresolved calls may create substantial downward bias in the observed late fraction, especially for real-time monitoring. This dashboard is a review aid, not a live emergency alarm or dispatch control system.

Validate identifier uniqueness, timezone awareness, arrival after dispatch, and plausible durations against source records. Preserve genuine extremes; investigate clock errors before correcting them and retain an audit trail. Set the target with local policy owners before examining the results. Collect a reference period under a stable policy that covers normal demand, weekends, and shifts, and freeze it before monitoring. Twenty days is only a demonstration default and may be insufficient operationally.

Use priority filters and comparable zones before comparing outcomes. Future collection could add nonidentifying proxies such as shift, weather category, traffic category, units available at dispatch, and travel-distance band, provided staff can measure them consistently. Such variables can guide investigation but do not turn an observational comparison into a causal study. Evaluate burden and privacy before adding fields.

## Browser-local open-call demonstration

Use **Start dispatch** to record a nonpatient ID, zone, priority, and local dispatch time. The form rejects future dispatches and duplicate IDs. Active and overdue counts respect the selected priority; overdue means elapsed time strictly exceeds the selected target. Elapsed times refresh every ten seconds while the page is open. An overdue open call is visible operational context, not a completed response or a statistical control-chart signal.

Record an arrival using its actual local time (or the **Use now** shortcut when accurate), with optional delay context. The combined completed records are validated through the API before the call moves into the completed-call analysis and CSV export. Until then, open calls are excluded from all statistical denominators, percentiles, intervals, and CSV exports. Report their number alongside completed-call results and investigate missing arrivals; an apparently good completed-call fraction can coexist with overdue open calls.

Open calls and locally added completed records are stored in this browser, scoped to the selected demo or uploaded filename. For an uploaded file, reload that file to restore its source-specific additions. A different browser or source will not share this register. It is not a durable backup, shared dispatch console, notification service, or a live 911 integration; closing the browser stops display updates. Canceled calls, reassignment, exclusions, and correction history still need the complete external intake register. Damaged local storage produces an explicit warning and backup/clear controls rather than silently discarding the unreadable register.
